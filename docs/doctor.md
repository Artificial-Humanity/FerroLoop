# `fl doctor` and `GET /api/v1/doctor`

`fl doctor` observes this install, including hosted vendor versions and update settings. It
changes nothing. The Hub serves the same report to the Owner at `GET /api/v1/doctor`, and
FerroDeck renders it.

Code: `fl_core::doctor` (the pure engine: facts in, report out; no I/O), `fl_install::observe`
(the file-system gatherer: reads only), `fl_store::health` (read-only store verification),
`crates/cli/src/cmd/doctor.rs` (the command), `crates/hub/src/doctor_api.rs` (the route).

## Usage

```
fl doctor [--json] [--prefix PATH] [--db PATH]
fl doctor --fix <check-id>
```

* `--json` prints the report as JSON (below). Without it, the report is text.
* `--prefix PATH` looks for the install (and its `receipt.json`) under this absolute directory
  instead of `~/.local/share/fl`. `$FL_INSTALL_ROOT` isolates the whole default layout under one
  root, as for `fl install`. A prefix that cannot be an install exits 3.
* `--db PATH` (or `$FL_DB`) names the one store to verify. Without it doctor verifies the
  workspace state store and every project store the config binds, each once, at most 64.
* `--fix <check-id>` is parsed and refused: exit 3, `repairs are not implemented in this
  release`. A repair is an explicit, separate action with its own plan.

## Exit status

| Code | Meaning |
|---|---|
| `0` | No check failed. `warn`, `not-installed` and `unsupported` do not fail the run. |
| `1` | At least one check is `fail`. |
| `3` | `--fix` (not implemented), or a `--prefix` that cannot be an install. |

## Statuses

| Status | Meaning |
|---|---|
| `pass` | Positive evidence that the check holds. |
| `warn` | Works, but something differs from what the receipt or the build says, or could not be proven in full. |
| `fail` | A broken or unsafe state. |
| `not-installed` | The thing is not there: no receipt (unmanaged), no store, no vault, no UI bundle. Never `pass`. |
| `unsupported` | The proof cannot be made from what is available. Never `pass`. |

`overall` is `pass` only when every check is `pass`; otherwise it is the worst check, ranked
`fail`, `warn`, `unsupported`, `not-installed`.

## The checks

The seven install checks appear first in the following order.

**`G7.release-identity`.** The running binary's build stamp (`fl` for the CLI, `fl-hub` for the
Hub). `pass` only for a known commit built from a clean tree. `warn`: the commit is unknown, the
tree was dirty or its state is unknown, or the binary's commit, version or release id differs
from the receipt's release, or the receipt records no commit to compare with a known one. A source build is shown as `source-build` and is never presented as
an official release.

**`G7.receipt-integrity`.** The install receipt at `<prefix>/receipt.json`, parsed and validated
with the installer's loader. No receipt is `not-installed` with the detail `unmanaged (no install
receipt)`: an existing source build or manual deployment is unmanaged, neither healthy nor
broken. A valid receipt is `pass`. A receipt that is corrupt, of an unsupported `schema_version`,
invalid in a named field, larger than 8 MiB, not a regular file or unreadable is `fail`; it is
never treated as unmanaged. If no home directory is known the check is `unsupported`.

**`G7.path-ownership`.** Every path, alias and unit the receipt owns, probed with `lstat`,
`readlink` and a bounded hash. A match is `pass`. Files are opened `O_NONBLOCK|O_NOFOLLOW` and checked with `fstat`, so a
FIFO or symlink swapped in after the `lstat` is neither waited on nor followed. A file or unit that was edited (a different
hash, the unit still carrying its `generated by fl install` marker) or a link that points
elsewhere is `warn`. A missing path, one of the wrong kind, a unit with no marker and a
different hash (foreign), or an unreadable one is `fail`. With no receipt the check is
`not-installed`; with an unusable receipt it is `unsupported`. Catalog entries and config blocks
the receipt records are named in the detail and not compared in this release. Hashing stops
after a time budget (60 s in the CLI, 5 s in the Hub); paths not reached are `warn`.

**`G7.store-health`.** Each store is opened read-only and never migrated or repaired:

* a `.fls` is read with `ferrostore::inspect_at` (`O_RDONLY`, no lock, both superblock slots and
  the live state);
* a `.redb` is opened with `RedbStore::open_read_only` (a shared lock, no write, waiting at most
  about 300 ms for a writer).

A store at a format this build reads is `pass`. A `.fls` held open by a live writer is verified
at once: reading it takes no lock. A format or container a newer fl wrote, or one
off the supported ladder, is `fail`; so is a store that is corrupt or not initialised. A lone
`.redb` that a normal open would migrate to `.fls` is `warn`: `doctor does not migrate`. A store
held by a writer is `warn`. A `.redb` that was not closed cleanly (it is valid, but only a normal
open can recover it) is `warn`: `needs recovery by a normal open (doctor does not repair)`; a
file that is garbage stays `fail`. A `.redb` beside a `.fls` is the migration backup and is mentioned,
not checked as current data. An absent store is `not-installed`. A list that may be incomplete
(an unreadable config) is at best `warn`. The writer-held `.redb` case relies on Linux `flock`
semantics (a second open file description conflicts with the writer's lock, even in one
process), as does its test.

**`G7.vault-perms`.** The vault file (`vault.enc`) and the master key file, found where FerroGate
looks for them. Only `lstat` is used; the files are never opened. A file readable, writable or
executable by its group or others is `fail` (a world-writable file says so); so is one owned by
another user, a symlink (FerroGate refuses it) or one that is not a regular file. A mode that is
owner-only but not `0600` is `warn`, as is a parent directory writable by its group or others, and
a vault with no master key file or `FL_VAULT_MASTER_KEY` (opening it would generate a new key).
Neither file present is `not-installed`. A platform that reports no modes is `unsupported`.
A directory that `fl` creates for these files, or for the other files in `~/.config/fl` (the hub
tokens, `operators.json`, `config.toml`), is mode `0700` at most, whatever the umask (the umask
can only narrow it, never widen it); only that leaf directory, not a parent such as `~/.config`. `fl` never changes the mode of a directory that
already exists, so a loose one made by hand or by an older `fl` is reported here and not fixed.

**`G7.code-ui-agree`.** The UI bundle's `build-info.json` against the binary's commit (the rule
of `GET /api/v1/version`). The CLI looks in `[hub].ui_dir` of the config, else
`<prefix>/current/ui/dist`; the Hub looks in the directory it serves. The same commit is `pass`
(the UI commit may be abbreviated to 7 digits or more); if either side was built from a dirty
tree it is `warn`. Different commits are `fail`. No bundle is `not-installed`. A bundle with no
valid `build-info.json`, or a binary whose commit is unknown, is `unsupported`.

**`G7.unit-order`.** Installed `ferro*.service` files in the layout's user unit directory
(`~/.config/systemd/user`, or `<root>/.config/systemd/user` under `$FL_INSTALL_ROOT`). The
names looked for include `ferrostore.service`, `ferrostore@.service`, `ferrowire.service` and
`ferroloop-hub.service`. A unit whose `[Install]` `WantedBy=` names `default.target` and whose
`[Unit]` `After=` also names it is `warn`: that pair is a `systemd --user` boot ordering cycle
(`WantedBy=default.target` implies `Before=default.target`). The detail names the unit and
advises `fl install`, or removing `After=default.target`. A unit that cannot be read (a symlink,
anything that is not a regular file, or a file larger than 64 KiB) is `warn`. A directory that
cannot be listed, or a `~/` path with no home directory, is `unsupported`. No `ferro*.service`
file is `not-installed`. Comments and the same keys in the wrong section do not count. Other
unit names in the directory are not read.

**`vendor.version-drift`.** Compares passively identified installed versions with the most
recent known hosted launch version for each vendor component on this machine. The Codex CLI
and shared daemon have independent baselines. The installed daemon version comes from the
selected package, and the hosted baseline records the daemon observed at launch. The baseline
is per host and vendor, so it is kept when the Hub deletes superseded launch receipts or
decommissions a session. A launch that cannot identify a component does not replace that
component's last known version. A known version difference is `warn`. An opaque installation
or missing, unreadable, or writer-locked history is shown as `unknown`. Doctor reads selected
files and package paths and makes no vendor CLI call or daemon connection.

The CLI finds the latest valid observation for each component across the configured Hub store
and the workspace store. The Hub store resolves to `[state].store` when configured, or to the
project store bound to the current directory when present. `--db` or `FL_DB` confines the CLI to
the named store. FerroDeck uses its serving Hub's store.

**`vendor.update-policy`.** Shows the update setting observed in this invocation's environment
or the vendor's user or managed configuration, alongside the policy applied to hosted CLI
launches. A documented enabled setting on an available runtime is `warn`. The Codex client startup
setting and the shared daemon's own updater setting are independent. The hosted CLI policy
applies to the client; the shared daemon reads its own settings. Doctor reports settings on
disk, so the running daemon may still have different settings. Settings that cannot be proven
passively are shown as `unknown`, followed by a short fixed reason in parentheses, for example
`codex daemon: configured unknown (shared daemon; settings.json failed validation)` or
`grok CLI: configured unknown (GROK_CONFIG_PATH overlay), hosted launch disabled`. A reason
names only a file or a variable and the problem (`unreadable`, `not a regular file or too
large`, `failed validation`, `unrecognised value`, an overlay, an unavailable configuration
directory). It never includes file contents, values, account identifiers or secrets. The JSON
shape does not change: the reason is part of `detail`.

Settings files are read passively: at most 1 MiB, opened `O_NONBLOCK` and checked with
`fstat`. A FIFO or other non-regular file is not waited on, and is `unknown`. Doctor opens
settings files `O_NOFOLLOW`, so a settings file that is a symbolic link is `unknown`. Claude
managed settings files are the only exception (see below). A missing file is the vendor
default.

The Codex shared daemon validates its whole `settings.json`. When that validation fails, Doctor
shows `unknown`. It cannot tell whether Codex then falls back to its defaults, which would turn
automatic updates on, or keeps the last valid settings.

Claude Code reads `DISABLE_AUTOUPDATER` and `DISABLE_UPDATES` from settings files and from the
process environment. A settings file `env` value replaces the same variable from the
environment. `1` and `true` (any case) disable updates. `0` and `false` (any case) and an empty
value leave them on. Other values are `unknown` (`unrecognised value`).

For the configured row, Doctor resolves each variable in Claude Code's documented order,
highest first. The first source that sets the variable decides it:

1. Managed settings files: `managed-settings.json` in the managed directory, then each `*.json`
   file in its `managed-settings.d/` in name order. A later file replaces an earlier value.
   Hidden files are skipped. An empty file counts as `{}`. The managed directory is
   `/etc/claude-code` on Linux and other Unix systems, `/Library/Application Support/ClaudeCode`
   on macOS, and `C:\Program Files\ClaudeCode` on Windows.
2. The `env` block of the user `settings.json` in `$CLAUDE_CONFIG_DIR`, or `~/.claude` when
   that variable is not set.
3. The process environment.

A missing file sets nothing. A file that exists but cannot be read or fails validation makes
each variable it could decide `unknown`, with a reason such as
`managed-settings.json failed validation`. Validation requires a JSON object whose `env`, when
present, maps names to strings. More than 64 drop-in files is `unknown`
(`managed-settings.d has too many files`), and so is more than 256 entries of any kind in
`managed-settings.d/` (`managed-settings.d has too many entries`). If either variable resolves
to disabled, updates are disabled.

Claude Code follows a managed settings file or drop-in that is a symbolic link, so Doctor
follows it too. Sites often link managed settings from a configuration-management checkout.
The target must be a regular file. A link to a FIFO, device or directory is `unknown`, and is
not waited on. A link whose target is missing reads as a missing file and sets nothing, as it
does for Claude Code. Doctor still does not follow a link at the user `settings.json` or any
other settings file.

Doctor does not read project or local settings files (`.claude/settings.json` and
`.claude/settings.local.json`), because they depend on the working directory. Those files
outrank the user file, so they can change the configured result in a project. Doctor cannot
observe remote server-managed settings from claude.ai either. They outrank the managed files.

Claude Code can also get managed settings from an MDM or OS policy. On macOS this is a
configuration profile in the `com.anthropic.claudecode` managed preferences domain. On Windows
it is the `Settings` registry value under `HKLM\SOFTWARE\Policies\ClaudeCode`. These policies
outrank the managed files. On Windows, Claude Code can also read the same value under
`HKCU\SOFTWARE\Policies\ClaudeCode` when no administrator source is present. Doctor does not
read the configuration profile or the registry.

Hosted Claude launches pass `--settings '{"env":{"DISABLE_AUTOUPDATER":"1"}}'` as well as the
environment switch. `--settings` outranks the project, local and user files, so only managed
settings can override it. The hosted row is `disabled` unless a managed file sets
`DISABLE_AUTOUPDATER` to a value that keeps updates on (`enabled`), or a managed file cannot be
read or fails validation (`unknown`). Remote server-managed settings, the macOS configuration
profile and the Windows registry policy can also override it, because they outrank
`--settings` like the managed files. Doctor cannot see them.

## JSON contract

```json
{
  "schema_version": 1,
  "overall": "warn",
  "summary": { "pass": 0, "warn": 1, "fail": 0, "not_installed": 8, "unsupported": 0 },
  "checks": [
    { "id": "G7.release-identity", "title": "Release identity", "status": "warn", "detail": "..." }
  ]
}
```

* `checks` starts with the seven `G7.*` IDs, followed by `vendor.version-drift` and
  `vendor.update-policy`. Each check has exactly `id`, `title`, `status` and `detail`.
  `status` is one of `pass`, `warn`, `fail`, `not-installed`, `unsupported`.
* The report has no timestamp. Equal inputs give equal bytes; lists are sorted and bounded.
* Schema version 1 supports additional checks in the `checks` list. A reader can render each
  check by its fields, including checks with unfamiliar IDs.

## `GET /api/v1/doctor`

Owner only: a Peer gets 403 `{"error":"owner authority required"}`, an unauthenticated caller
401. The answer names filesystem paths and permissions. The Hub reports on its own context: its
build stamp, the receipt under `$FL_INSTALL_ROOT` or its home directory, its configured store,
its vault files and the UI directory it serves. Vendor evidence uses the Hub process's
environment, home directory and configured store. Store verification and vendor history reads
run without the Hub's store lock, so no other request waits behind them.

## What doctor never does

It makes no network call, runs no subprocess, loads no model and spends no tokens. It generates
no key, creates no file or directory, migrates or repairs no store, takes no write lock, restarts
no service and edits no configuration. It never reads the vault's contents and prints no secret
(it prints a path and a mode, and the receipt's own text only when the loader names a field).
