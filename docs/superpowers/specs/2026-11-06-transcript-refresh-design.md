# #363 — preserve same-session history during unavailable refresh (proposal)

Design-only handback for Ferris; no source edits, live transcript reads or probes. Source reviewed at cached origin/main44e1bdfc; references below identify functions rather than claiming a live runtime trace.

## Established source cause

`TranscriptReads::raw` (discovery.rs, ~3025) deliberately returns None if file identity/stamps change across a read; `after_next_transcript_read` can trigger that deterministically. GET `/sessions/:id/transcript` (api.rs~4827-4855) converts `all_observation.unwrap_or_default()` to HTTP200/turns[]. App refresh then applies/caches the empty array; the next stable poll restores turns. App's initial-load effect additionally clears turns on rejection. ChatPane's standalone fetch guards only the target string, not same-target request/reset generations. A separate source gap: `transcript_observation_from_sessions` also returns Some(empty) when no source was found; that is not evidence that a real transcript was empty. No live transcript body is needed to prove these paths.

## Recommended smallest API/UI contract

**API:** Stop returning successful empty history for an unavailable observation. Return HTTP503 with bounded `code: transcript_unavailable` and a small reason enum (`unstable_or_unreadable`, `source_not_available`); do not include turns[] or private paths/error strings. Existing non-2xx handling is safer for older clients than a new 200 flag they ignore. Preserve existing transcript and attempt-output fallback precedence: an observed zero-turn source still falls through to the remaining sources, including a matching attempt excerpt. Only after those fallbacks are exhausted does a stable observed/parsed zero-turn result remain HTTP200/turns[] and replace last-good history. Successful observed nonempty history is unchanged; distinguish this final observed-empty result from having observed no source at all.

To make that distinction truthful, the GET path needs a small source-observation result distinguishing observed(empty/nonempty), unavailable read, and no source; retain existing compatibility helpers for queue/busy consumers. No new vendor calls, reread retries or parser redesign. A missing route/session/source is unavailable, not confirmed-empty; do not invent a 404/retirement fact from one discovery miss. If later distinct not-found semantics are desired, select them separately. Stable parsed-empty means zero displayable turns under existing parsers, not proof of model consumption/reset.

Return additive `resolved_session_id` when resolution actually proves it; keep existing request `session_id` echo for compatibility. An unresolved persona alias is not proof that the old concrete session is still current. No server-side history cache or persistent format is needed. Endpoint's existing queue-drain/busy behavior is not redesigned here.

**UI:** Retain last-good turns only under the same authenticated principal, selected agent AND concrete session, and local view/reset generation. Only for transcript-unavailable responses or transient/network read failures, keep that exact-key history with `History refresh unavailable; showing last loaded history`; with no last-good data show loading/unavailable, never the no-history empty state. Authentication/authorization failures (401/403) follow existing auth/access handling, not this stale-history path, and must not retain or display prior-principal history. Successful observed empty history is applied normally; do not ignore all empty arrays or infer state from assistant prose/timing/optimistic Operator rows. Unknown/unresolved aliases must not reuse an unrelated concrete-session cache.

Use one small consistent response-acceptance rule in App's poll/load/initial/background reads and ChatPane's standalone fetch: capture owner key, auth/selection/reset epoch and monotonically increasing request sequence; apply result/error/finally only if all still match. Reject old overlapping responses even for A→B→A or the same target; unmount/logout/principal change invalidates them. Background badge caches cannot be installed as selected chat history unless their concrete-session ownership matches. Existing persona-only cache is insufficient for that check. Render only matching-key data immediately on selection change, not one paint of another target pending effect cleanup.

Explicit successful Clear/Reforge/teardown invalidates the old last-good/cache/optimistic view for that target and increments the local reset generation; an older in-flight response cannot restore it. Beginning reset invalidates outstanding requests; while reset is pending do not commit their responses. A failed reset retains last-good with its error. Refetch under the new generation after completion. This is local stale-response control, not a claim that vendor reset was consumed. Preserve existing queue uncertainty/holds, drafts and delivery receipts; transcript errors cannot imply successful send or trigger resend. Keep independently observed queue metadata separate from transcript absence rather than synthesizing an empty queue/idle state.

## Deterministic acceptance tests (proposed; not run)

- Hub temp HOME/store: stable populated GET, then `after_next_transcript_read` rewrites/removes fixture after bytes are read →503/no fabricated turns; next stable GET restores history. Ensure the hook hits the transcript observation, not an unrelated earlier read. Test a stable truly empty file with no later fallback→200[], absent source→unavailable, and observed empty followed by a matching nonempty attempt excerpt→200 with the excerpt, preserving existing fallback precedence. Stub delivery/queue activity so tests make zero real dispatches.
- UI App and standalone ChatPane: populated→503/network failure→recovery keeps exact-key history, stale notice clears only on accepted recovery. Initial unavailable shows no stale unrelated turns/no false empty state. Observed200[] really clears. Classify 401/403 separately from transient/network failures: invoke existing auth/access handling and never retain prior-principal history or show a generic stale-history notice for denied access.
- Deferred responses: newest-first/oldest-last, newer failure then older success, agent A→B→A, same agent/different session, unresolved alias, logout/relogin, unmount. Neither turns nor cache/status/error/busy/queue fields may cross ownership or overwrite newer state.
- Successful and failed reset with an outstanding pre-reset request; success cannot resurrect old history, failure does not erase good history. Optimistic prompts/drafts and unconfirmed holds remain protected. Test same-agent cache ownership explicitly.

## Alternatives/material selection

Recommend 503 + minimal typed source observation, additive resolved identity, and keyed UI last-good/stale state. A200 availability discriminator requires changing every consumer and lets older clients still wipe history; server-side stale caching adds retention/invalidation machinery unnecessarily. An API-only503 patch is insufficient because the load-effect catch clears history and same-key stale responses remain possible. Select this bounded contract before implementation. Proposed footprint: hub GET/read-observation helper, API type/client error handling as needed, App/ChatPane refresh-state controls and isolated tests; no delivery/peer/host/backend correlation work. Coordinate Felix before actual UI edits. Fresh implementation/review and focused+full UI/build/affected Rust checks follow only after Lead execution disposition.
