# FerroWatch per-agent usage — design proposal

Status: draft for review. Issue #495, phase 1. This document records implementation choices, not owner ratification.

## Purpose and scope

Report locally observed token consumption per persona, vendor and model over arbitrary time windows. Attribute Antigravity internal conversations to their parent persona; retain counted history after transcript removal. Expose the same data through `fl watch usage`, an Owner-only hub endpoint, and a sortable FerroDeck table. Do not store transcript content. Alerts, budget conversions and balance planning remain out of scope.

## Approaches

1. **Durable normalized per-event rows and per-source checkpoints (proposed).** Persist timestamped counters and stable event identity; query aggregates these rows for any window. A checkpoint is an optimization, not the source of truth. This supports late attribution and exact time filters, and deterministic identities make replay safe. It requires bounded store operations and explicit source reset handling.
2. **Per-source aggregate snapshots with offsets.** Write counters and offset together in a single state entry. This is compact, but arbitrary time windows require retaining timestamped buckets, and unbounded entries or independent offset/rollup writes introduce correctness and recovery problems.
3. **Recompute from transcripts on request.** Simple aggregation, but violates incremental scanning and loses history on deletion. Not suitable.

## Collection and storage

- Implement a shared FerroWatch usage model and query layer. A single hub-owned collector discovers files and appends only bytes after a durable offset; CLI reads durable usage rows from the workspace store, so offline reports work and the CLI does not race the hub scanner. Do not run collectors on GET request threads. A first scan reads existing files once; later scans seek from their last complete newline, leaving a partial line for the next scan. Bound bytes, line sizes, files and work per cycle; expose pending/error state instead of silently reporting complete.
- Persist normalized count-only records keyed by source identity and stable event identity, with timestamp, vendor, model, conversation ID, optional parent ID, resolved persona or unresolved attribution, token counters, turn count and subagent count. Do not persist message text, prompts or arbitrary transcript fields. Support exact lower bounds for custom windows; do not reduce all data to daily totals.
- Define a dedicated usage-store batch operation that atomically validates the expected source generation and cursor, writes deterministic normalized observations and the resulting checkpoint, and commits or refuses as one transaction. Implement and test it for ferro (including its remote transaction path) and redb; if a backend cannot provide the guarantee, return an explicit unsupported error rather than silently weakening it. Do not use a plain `StateStore::upsert_state` read-modify-write as cross-process CAS. Serialize collector scheduling as a performance measure, not as the sole correctness mechanism. Bound each batch and query by source/time, measure growth and avoid one indexed State revision per token event. Crash before commit must change neither data nor cursor; retry of a committed batch must be recognized or safely replayed. Test concurrent writers, crash and restart across both backends.
- Identify files by stable file identity as well as path; detect rotation, replacement and truncation. For formats with stable event IDs, deduplicate across generations. For ambiguous rewritten sources, avoid silently adding a second copy: record an incomplete/reset diagnostic until safe recovery is possible. Preserve already stored events when source files disappear. Handle malformed and incomplete records without skipping later valid data or persisting raw data.
- Maintain durable session-to-persona associations from hosted records, routes, tombstones and passive identity with provenance. Never attribute ambiguous identities to a guessed persona. Persist unresolved counts and retry attribution when parent or persona mapping arrives, so late discoveries and decommission do not drop or double count historical usage. Internal Antigravity parent references are parsed in memory and only the parent ID is retained; guard cycles, missing parents and duplicate subagent counts.

## Vendor semantics

- Antigravity: establish which usage-bearing step kinds represent charged calls from sanitized fixtures and the manual comparison; the existing `PLANNER_RESPONSE` parser only reads latest context and is not proof that other usage-bearing steps can be ignored. Parse event timestamp, model and conversation identity from logs; resolve internal conversation to parent from its message step and metadata independently of usage records. Establish stable event identity across `transcript.jsonl`, `transcript_full.jsonl`, rewinds and repeated records; do not equate a reused step index with the same charged call without evidence. Verify on fixtures and the retained 2026-11-08 to 2026-11-10 data against the manual reference.
- Codex: parse rollout `event_msg` / `token_count` `payload.info` fields, tracking cumulative totals and deriving deltas only for new observations; repeated snapshots must not count again. Commit the cumulative baseline with observations and cursor in the same batch. Detect partial resets and model changes; do not treat cumulative snapshots as independent turns or infer turns without evidence. The issue's `/payload/event/usage` pointer is used by Muse `model_completed`, not the Codex parser. Verify actual fields and turn semantics against sanitized fixtures.
- Claude: parse assistant message usage, accounting for multiple streamed entries of one message without duplication and revising the materialized count when a later observation corrects it; input, cache creation, cache read and output are separate fields. Identify model and time from each event.
- Muse: parse `runtime.session` / `model_completed` usage when exposed. Grok: inspect local signal/summary formats; if counts or timestamps are not available, expose no data, not zero. Mark unsupported token categories unavailable rather than inventing numbers.
- Use UTC timestamps and a half-open window `[since, now)`; records lacking timestamps stay separately reported as undated and are not silently included in an exact window. Count a distinct Antigravity subagent once at its recorded launch time, not once per token event; unknown launch time is reported separately. Historical data deleted before any collection cannot be recovered and coverage must say so. Token fields preserve vendor meanings. Do not silently add cache counts to input or compare across vendors as identical billing units. Missing model, time or identity is visible as unknown/unattributed, not dropped or fabricated.

## Interfaces

- `fl watch usage [--since 48h] [--by persona|vendor|model] [--json]` reads durable workspace rows locally, even when the hub is offline; only the hub collector scans transcripts. Validate time ranges and grouping; default to 24 hours and persona grouping. Report source completeness, last successful scan, unavailable categories and unattributed totals.
- `GET /api/v1/usage?since=…&by=…` checks Owner authority explicitly before data access. Accept an absolute timestamp or duration for `since`; return normalized rows, units, range and collection status. Reject malformed input with 400 and peer access with 403. No transcript content is returned.
- Add a sortable usage table to the existing FerroWatch view, using the API's existing visual language and explicit loading, empty, stale and error states. Show input, output, cache read/write, turns and subagents. Seven-day per-agent sparkline only if it can be supplied without another costly scan; it is optional in phase 1. Keyboard sorting and responsive layout are required.

## Verification and rollout

Fixture tests for each supported parser, alternate/missing fields, duplicate records and counters, model changes, partial lines, source replacement, late parent/identity binding and deleted transcripts. Test concurrent scans and crash/restart at each storage boundary on both ferro and redb backends, along with owner/peer API authorization, CLI JSON and formatting, and the FerroDeck table. Run the repository verification trio, UI tests/build, and live isolated hub checks with Playwright and Chrome DevTools including console, network and keyboard accessibility; close pages afterwards. Compare the retained Antigravity window with the manual approximately 17.4M input, 1.5M output and 247M cache-read; report coverage and discrepancy without exposing transcript contents. Never mutate live source transcripts.

## Open implementation checks

Confirm actual source-specific event and turn identities, timestamp fields, rotations, the parent-link representation, the dedicated transactional batch implementation on both backends and bounded range-query cost before finalizing the plan. Clarify whether the manual totals use inclusive window endpoints and what retained-conversation coverage is. If a source cannot supply a safe deduplication key or a source format's counters are ambiguous, label its data incomplete rather than claiming exact totals.
